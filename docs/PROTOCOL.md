# Aegiron protocol (v1)

> The product was called ReDesk before 0.5.0. Signature and key-derivation labels (`redesk-register-v1`, `redesk-server-v1`, `redesk-kx-v1`, `redesk v1 …`), the vault AAD and the LAN discovery magic keep that name on purpose: they are part of the wire format, so agents, servers and stored secrets from before the rename keep working. The server also accepts the old `X-ReDesk` header and `REDESK_*` environment variables.

Everything runs over one HTTPS port (default `21114`): REST API, agent signaling (`/ws/agent`) and the relay (`/ws/relay`).

## 1. Agent registration (`/ws/agent`, text JSON)

The agent pins the server's Ed25519 public key at `init` time.

```
server → agent  {"t":"challenge","nonce":S}
agent  → server {"t":"register","id","pk","nonce":A,"sig","hostname","os","version","enroll_token"?,"macs"?,"lan"?}
                sig = Ed25519(agent_key, "redesk-register-v1\n" + id + "\n" + S + "\n" + A)
server → agent  {"t":"registered","sig":Ed25519(server_key, "redesk-server-v1\n" + id + "\n" + A + "\n" + S),"policy":{...}|null}
             or {"t":"error","code":"id_taken|id_changed|enroll_required|disabled|bad_signature|...","message","id"?}
```

- Device IDs: 9 digits as generated by the agent; an admin may set a custom ID of 9-16 digits or 6-32 characters `a-z 0-9 _ -` starting with a letter (see [Device IDs](#device-ids-and-strategies)).

- The first registration binds `id → pk` (TOFU per device). A different key for the same id is rejected (`id_taken`) and audited as `device.key_mismatch`. Admins can reset the binding.
- With `require_enroll` on, a new or reset device must present a valid enrollment token.
- If the server signature fails verification, the agent aborts: *invalid public key from server*.
- Keepalive: `{"t":"ping"}` / `{"t":"pong"}` every 20 s.
- `macs` (up to 16, `aa:bb:cc:dd:ee:ff`) and `lan` (`[{ip, prefix}]`, up to 16) describe the device's network so the server can wake it later. Admins see them; other users only see `can_wake`.
- Wake-on-LAN: `POST /api/devices/{id}/wake` picks an online agent on the same LAN (same public IP and/or subnet) and sends it `{"t":"wol","macs":[...],"target":"<id>"}`. The helper broadcasts the magic packet (UDP 9 and 7) and reports `wol_sent`. Errors: `online_already`, `no_mac`, `no_helper`, `helper_busy`, `rate_limited`.
- LAN discovery (not through the server): a viewer broadcasts `redesk-discover v1` to UDP 21120; agents on the same subnet with `lan_discovery = true` answer `{id, hostname, os}`, rate-limited.
- Session request: `{"t":"session","sid","token","relay":"/ws/relay","viewer":{"email","name","ip"}}`.
- Agent → server audit events: `{"t":"event","sid","kind","detail"}` with `kind` in `auth_failed | auth_ok | denied | locked | file_upload | file_download | wol_sent`, plus the file, recording and [session control](#session-controls) kinds below. They are stored as `agent.<kind>` and attributed to the viewer of that session; unknown kinds are dropped.

### Device IDs and strategies

**Custom IDs.** `POST /api/devices/{id}/change-id {"id"}` (admin) renames a device (spaces are dropped, letters lowercased; `409 id_taken` if another device has it). Address books, sessions and recordings follow the device; the audit log keeps `device.id_changed {from, to}`. An online agent gets `{"t":"id_changed","id"}` over signaling, saves the new ID and reconnects with the same key. An offline agent learns it at its next registration under the old ID: the server answers `{"t":"error","code":"id_changed","id":<new>}`, but only when the registering key is the device's key; any other key gets `id_taken`. The old ID stays reserved until the agent registers under the new one. Agents before 0.6 do not know `id_changed` and keep failing to register until updated.

**Strategies** (RustDesk "strategy"): admin-defined bundles of agent settings, `GET/POST /api/strategies`, `PUT/DELETE /api/strategies/{id}` (`{name, description, settings, group_ids}`). A strategy is assigned to device groups (`group_ids`, one strategy per group) or to one device (`PATCH /api/devices/{id}` with `strategy_id`; absent = unchanged, `null` = follow the group). The device's own strategy wins over its group's. `settings` only contains managed keys:

| key | values | effect on the agent |
|---|---|---|
| `approve_mode` | `password` \| `click` \| `both` | how sessions are accepted |
| `allow_permanent_password` | `false` | one-time passwords only; the stored permanent password is removed |
| `allow_input`, `allow_clipboard`, `allow_file_transfer`, `allow_audio`, `allow_whiteboard`, `allow_resolution` | bool | session permissions |
| `allow_block_input`, `allow_privacy_mode`, `allow_lock`, `allow_restart` | bool | session controls a viewer may use |
| `allow_tunnel`, `allow_tunnel_lan`, `allow_terminal` | bool | TCP tunnels (and whether they may reach other LAN hosts) and the remote terminal (§11) |
| `direct_enabled`, `lan_discovery` | bool | direct/P2P sessions, LAN discovery answers |
| `lock_after_session` | bool | lock the screen whenever a session ends (done by the session controls, without needing `allow_lock`) |
| `record_sessions` | `true` | enforced by the server: every session to the device is recorded whatever `GET /api/recordings/settings` says |

The effective strategy goes to the agent as `registered.policy` and, when an admin changes strategies, groups or devices, as `{"t":"policy","policy":{"id","name","settings"}|null}`. The agent stores it in `agent.toml` (`[managed]`, so it also applies offline) and writes the managed values over its own on load, on receipt and after every change in the app. Settings shows those rows faded with *จัดการโดยองค์กรของคุณ*, and `aegiron-agent set` / `set-password` refuse them. With no strategy (`null`, or an older server) everything stays local; when a strategy is removed the values stay but become editable. Older agents ignore `policy`. Audit: `strategy.created|updated|deleted`, `device.updated {strategy_id}`.

## 2. Relay (`/ws/relay?sid=&token=`)

The viewer token goes only to the console user who requested the session, and the relay also requires that user's login cookie. The agent token is sent over signaling. Once both sides connect, the server sends `{"t":"paired"}` to each and then forwards frames **blind**. It counts bytes for the audit log but cannot read the content.

## 3. E2E handshake (text JSON through the relay)

```
viewer → agent  {"t":"hello","v":1,"epk":X25519 public (32B, base64)}
agent  → viewer {"t":"hello","v":1,"epk":...,"sig":Ed25519(device_key, transcript)}

transcript = "redesk-kx-v1" || sid || viewer_epk || agent_epk
```

The viewer verifies `sig` against the device public key fetched from the API. That key was bound at registration, so a relay or server that swaps keys cannot impersonate the device. The UI shows the key's fingerprint, which can be compared with `aegiron-agent info`.

```
shared  = X25519(viewer_esk, agent_epk)
salt    = SHA-256(transcript)
k_v2a   = HKDF-SHA256(shared, salt, "redesk v1 viewer->agent", 32)
k_a2v   = HKDF-SHA256(shared, salt, "redesk v1 agent->viewer", 32)
AEAD    = AES-256-GCM, nonce = 0x00000000 || u64_be(counter), one counter per direction
```

Every later message is binary ciphertext. A dropped, reordered, or replayed message fails decryption because the counter is implicit.

## 4. Messages inside the encrypted channel

Byte 0 is the type: `0x01` JSON, `0x02` video rectangle (`x, y, frame_w, frame_h` as u16 BE, followed by a JPEG), `0x03` file chunk (transfer id as u32 BE, followed by up to 64 KiB of data), `0x04` video frame (codec u8 `1` = H.264 or `2` = AV1, flags u8 with bit 0 = keyframe, `width, height` as u16 BE, followed by one access unit: Annex B for H.264, one temporal unit of low-overhead OBUs for AV1), `0x05` audio packet (see [Audio](#audio)), `0x06` message of an extra display stream (see [Displays, resolution and input modes](#displays-resolution-and-input-modes)), `0x10` tunnel data and `0x11` terminal data (tunnel and terminal sessions only, see §11).

| Direction | Message |
|---|---|
| agent→viewer | `auth_required {password, click}`, `auth_pending`, `auth_result {ok, reason?, attempts_left?, retry_after?}`, `info {hostname, os, displays[], input, clipboard, files, codec, codecs?[], features?, encoder?, audio?, audio_codec?}`, `encoder {encoder,codec}`, `cursor {x,y,visible}`, `clip {s}` |
| viewer→agent | `auth {password, codecs[], features?[], audio?[], resume?}`, `audio {on}`, `mm {x,y}`, `mb {b,down,x,y}`, `wh {dx,dy}`, `key {code,key,down}`, `text {s}`, `clip {s}`, `cfg {fps,quality,max_width,display,codec?}`, `refresh` (alias `keyframe`), `bye` |
| files viewer→agent | `ls {path}` (`""` = home), `put {id,dir,name,size}` followed by `0x03` chunks and then `put_end {id}`, `get {id,path}`, `cancel {id}` |
| files agent→viewer | `ls {path,parent,sep,entries[{name,dir,size,mtime}]}`, `put_ok {id,path}`, `put_done {id,path}`, `get_start {id,name,size}` followed by `0x03` chunks and then `get_end {id}`, `fs_error {op,id?,message}` |

### Video codecs

The viewer lists the codecs it can decode in `auth.codecs`, best first (`["h264","av1","jpeg"]`, or `["av1","h264","jpeg"]` when the user picked AV1). The agent picks AV1 only when it comes before `h264` in that list and this machine has an AV1 encoder; otherwise H.264 when offered, otherwise JPEG. It reports the choice in `info.codec`. H.264 stays the default: 0.4/0.5 viewers send `["h264","jpeg"]` and 0.4/0.5 agents pick H.264 whenever it is listed, so a list that starts with `av1` still gets H.264 from them.

- **H.264** (OpenH264, Constrained Baseline, screen-content mode, rate control from resolution × fps × quality): whole frames as `0x04`, sent only when the screen changed. A keyframe goes out at start, after `cfg` changes, on `refresh`/`keyframe`, and every ~10 s of activity. Browsers decode with WebCodecs (`avc1.42E033`) and the native app with OpenH264. A viewer drops deltas until its first keyframe and sends `keyframe` after a decoder error. If the agent's encoder fails, it falls back to JPEG rectangles in the same session, so every viewer must accept both.
- **AV1** (opt-in, hardware encoder only): whole frames as `0x04` with codec `2`, same keyframe and change-only rules as H.264. Each payload is one temporal unit in the low-overhead OBU format (AV1 spec section 5), and every keyframe carries the sequence header, so decoders are configured without a description. Browsers decode with WebCodecs (`av01.0.08M.08`, a higher level above 2048×1088) and the native app with rav1d. Only offered by a viewer that can decode it (the browser checks `VideoDecoder.isConfigSupported`).
- **JPEG** (fallback): only the changed bounding rectangle as `0x02`.

`info.codecs` (agents from 0.6) lists the codecs this session can switch to: the viewer's list, limited to what the agent can encode (`av1` only with an AV1 encoder). The viewer switches with `cfg {codec}`; the agent ignores codecs not in `info.codecs`, starts the new codec with a keyframe and announces it with `encoder`. Viewers pick the decoder from the codec byte of each `0x04` frame and, after a change, drop deltas until the next keyframe. Older agents ignore `cfg.codec` and send no `info.codecs`.

The app chooses in Settings → General → Codec เมื่อควบคุมเครื่องอื่น (`viewer_codec` in the config, `h264` or `av1`, default `h264`; `aegiron-agent connect --codec av1` for one session) and per window in การแสดงผล → Codec วิดีโอ. The web viewer remembers the choice from its quality menu (การแสดงผล → Codec วิดีโอ) in the browser. Both show the codec actually in use in the menu and the quality monitor.

### Video encoders

Each codec has one or more encoders behind it; the agent picks one per session and reports it in `info.encoder`:

| `encoder` | Where | Notes |
|---|---|---|
| `videotoolbox` | macOS | Hardware only (`RequireHardwareAcceleratedVideoEncoder`), Constrained Baseline (Baseline before macOS 12), real time, no frame reordering, BT.601. AVCC output is rewritten to Annex B with SPS/PPS before every IDR. |
| `mediafoundation` | Windows | First hardware H.264 MFT that accepts NV12 input (Quick Sync, NVENC, AMF), Baseline profile, low-latency mode. Not yet run on GPU encoders; CI runs the same code (types, NV12 input, output, keyframes) on Windows with Microsoft's software H.264 MFT. |
| `mediafoundation` (AV1) | Windows | First hardware AV1 MFT that accepts NV12 input (NVIDIA RTX 40, Intel Arc / Core Ultra, AMD RDNA 3 and newer), Main 4:2:0 8-bit, low-latency mode. The sequence header is copied in front of any keyframe that comes without one. Probed once per process; without one AV1 is not offered. Untested: no CI runner or test machine has an AV1 encoder yet. |
| `openh264` | everywhere | Software fallback, unchanged. |
| `jpeg` | | The session uses JPEG rectangles. |

All H.264 encoders produce Annex B Constrained Baseline, so `avc1.42E033` (WebCodecs) and OpenH264 (native app) decode any of them and nothing changes for older viewers. The choice is automatic: hardware, then OpenH264, then JPEG. AV1 is hardware only, so "software only" also turns AV1 off. The host can force software in the app (Settings → General → การเข้ารหัสวิดีโอ → ซอฟต์แวร์เท่านั้น) or with `aegiron-agent set --video-encoder software` (`video_encoder` in the config; default `auto`). If the encoder or codec in use changes during a session (the AV1 encoder fails and H.264 takes over, a hardware encoder fails and OpenH264 takes over, H.264 fails and JPEG takes over, or the viewer switched with `cfg {codec}`), the agent sends `{"t":"encoder","encoder","codec"}`. Viewers that do not know this message ignore it. Every viewer that offers AV1 also decodes H.264, so an AV1 failure never ends the session. `AEGIRON_HW_ENCODER=0` on the agent turns hardware encoding off. Older agents send no `encoder`; for H.264 that means `openh264`.

Why AV1 only in hardware, and no VP9:

- **rav1e** (pure Rust AV1 encoder) is too slow for live screens and holds frames back. Even with `low_latency`, `rdo_lookahead_frames = 1`, speed 10 and 8 tiles it returns a frame's packet only after about four more frames, and sessions send frames only when the screen changes, so the last change would not show until the encoder is fed the same frame again. `examples/codec_bench.rs` measures that (the frame re-sent until its packet comes out) against the H.264 encoders on synthetic text at 1920×1080 on an Apple M4 (10 cores): typing 126 ms median / 306 ms p95 per change for rav1e vs 6 ms VideoToolbox and 13 ms OpenH264; scrolling 346 ms / 887 ms vs 6 ms and 25 ms. At 1280×720 rav1e still takes 75–96 ms. Its x86 assembly would also need nasm. rav1e is a dev-dependency for the AV1 round-trip test and the benchmark only.
- **VideoToolbox** has no AV1 or VP9 encoder (Apple silicon up to M4 decodes AV1 in hardware but cannot encode it), so macOS agents never offer AV1.
- **VP9** would need libvpx, a C library: the crates either link a system libvpx (pkg-config), download prebuilt binaries at build time, or run its configure/make, none of which builds from cargo alone for both macOS architectures and mingw. Hardware VP9 encoders are rare (Intel only), and screen content gains little over hardware H.264.
- **libaom / SVT-AV1** need CMake and nasm.

rav1d decodes without assembly (the x86 code needs nasm and the published crate lacks the headers its ARM code includes): about 5 ms per 1080p frame for typing and 11 ms for scrolling on the M4.

### Audio

Byte `0x05`: audio packet: codec u8 (`1` = Opus, 48 kHz, stereo), sequence u32 BE (+1 per 20 ms frame), then one Opus packet (20 ms, about 96 kbit/s).

- The viewer lists the audio codecs it can play in `auth.audio` (`["opus"]`). If the list is missing or does not include `opus`, the agent never sends `0x05`, so older viewers are unaffected.
- `info.audio` (bool) says whether this session streams audio, and `info.audio_codec` names the codec (`"opus"` or `null`). It is true only when the viewer asked for audio, the device allows it (`allow_audio`, "อนุญาตเสียง" in the app), and the platform can capture: macOS 13+ (ScreenCaptureKit, using the Screen Recording permission, without the agent's own sound) or Windows (WASAPI loopback of the default output device). Linux sends no audio.
- Mute: viewer→agent `{"t":"audio","on":false}` stops `0x05` packets, and `on:true` resumes them. Older agents ignore it.
- Audio has its own queue of about 320 ms on the agent. Packets are dropped rather than delayed when the link is congested, so a sequence gap means dropped audio. Viewers play through a jitter buffer of about 80 ms: the browser uses WebCodecs `AudioDecoder` and Web Audio, and the native app uses Opus and the default output device.
- Tests: `AEGIRON_TEST_AUDIO=tone` in the agent's environment replaces capture with a generated tone (never set by the app or installers; see [TESTING.md](TESTING.md)).

Screen captures do not include the pointer, so the agent sends `cursor` (normalised to the streamed display, `visible=false` when it is on another display) whenever the pointer moves. Viewers draw it while their own pointer is not over the remote screen.

Uploads keep only the file name (any path the viewer sends is dropped), never overwrite an existing file (`name (1).ext`), must match the announced size, and are deleted if the session ends before `put_end`. Downloads are read on a separate task and share the session's back-pressured outbound queue with video.

### Folders and file management (`info.features` contains `"fs2"`)

Agents from 0.6 list optional capabilities in `info.features` (an array of strings; absent on older agents). Viewers only offer folder transfer, delete, rename, new folder and clipboard files when the matching feature is listed, so old agents and old viewers keep working with the single-file messages above. Everything here still requires the `files` permission; refused requests get `fs_error`.

| Direction | Message |
|---|---|
| viewer→agent | `put {id,dir,name,size,rel}`: like `put`, but `rel` is a path inside `dir` (`/`-separated, e.g. `"Photos/2024/a.jpg"`); missing directories are created |
| viewer→agent | `mkdir {id,dir,name}` (`dir` `""` = `~/Downloads/Aegiron`; `name` may be a relative path; the last component gets ` (1)` if it exists) → `fs_ok {op:"mkdir",id,path}` |
| viewer→agent | `get_dir {id,path}` → `dir_start {id,name,files,size,dirs[]}`, then for each file `dir_file {id,rel,size}` followed by its `0x03` chunks (same transfer id), `dir_skip {id,rel,message}` for unreadable files, and finally `get_end {id}` |
| viewer→agent | `rm {id,path}` (file or whole directory) → `fs_ok {op:"rm",id,path}` |
| viewer→agent | `mv {id,path,name}` (rename inside the same directory; fails if `name` exists) → `fs_ok {op:"mv",id,path}` (new path) |
| viewer→agent | `cancel {id}` now also stops a running `get` / `get_dir` |

Folder upload: the viewer sends `mkdir {dir, name:"<folder>"}` and uses the returned path (so an existing folder is never merged into: `Photos (1)`), then one `put {dir:<path>, rel}` per file (and `mkdir` for empty sub-folders), one after another. Folder download streams files one at a time; the viewer creates `dirs[]` (including empty ones) and writes each `dir_file` until the next `dir_file` or `get_end`. The browser saves a downloaded folder as `<folder>.zip`; the desktop app writes it under `~/Downloads/Aegiron/<folder>` (` (1)` if taken).

Relative paths are untrusted on both sides (agent for `put.rel`/`mkdir.name`, viewer for `dir_file.rel`/`dirs`): split on `/` and `\`; a path that is empty, absolute, has a drive/UNC prefix or contains `.`/`..` components is rejected; characters invalid on Windows (`<>:"|?*`, control characters) become `_`; a component is at most 255 bytes. While creating directories, an existing component that is a symlink or not a directory aborts that file, so a symlink inside the target cannot redirect writes elsewhere. `get_dir` never follows symlinks (they are skipped) and stops at 100,000 entries or depth 64. `rm` refuses the filesystem root and the home directory and removes a symlink itself, never its target. Every upload, download, delete and rename is reported as an agent event (`file_upload`, `file_download`, `file_delete`, `file_rename`).

### Clipboard files (`info.features` contains `"clipfiles"`; desktop app only)

Needs both the `clipboard` and `files` permissions. The viewer opts in with `auth {…, features:["clipfiles"]}`.

| Direction | Message |
|---|---|
| agent→viewer | `clip_files {files[{name,path,dir,size}]}`: files/folders were copied on the agent (macOS `NSPasteboard` file URLs, Windows `CF_HDROP`) |
| viewer→agent | `clip_files {id,paths[]}`: put these agent paths on the agent's clipboard as files → `fs_ok {op:"clip_files",id}` |

- **Viewer → agent (paste):** when ⌘V/Ctrl+V is pressed in the remote window and this machine's clipboard holds files, the app uploads them (folders included) to `~/Downloads/Aegiron` on the agent, puts the uploaded paths on the agent's clipboard with `clip_files`, then presses paste on the remote side, so pasting into Finder/Explorer copies them there. The files also stay in `Downloads/Aegiron` (the app says so), which is the fallback when the focused remote app does not accept files. Pressing paste again without copying anything new only presses paste remotely.
- **Agent → viewer (copy):** small selections (files only, at most 20 and 32 MiB in total) are fetched right away into a temporary folder and put on this machine's clipboard as files, so ⌘V/Ctrl+V in Finder/Explorer pastes them; larger selections and folders wait for the user to click *รับไฟล์* in the remote window, are saved under `~/Downloads/Aegiron` and then put on the clipboard. Files never flow to a viewer that did not opt in, and the agent does not echo back file lists it set itself.

### Session controls

Like RustDesk's: view-only, blocking the remote user's input, privacy mode, locking now or after the session, and restarting with automatic reconnection. The agent lists each control in `info.features` only when the device allows it and the platform can do it; viewers show a control only when it is listed, so older agents and viewers are unaffected. View-only also works against older agents, since it is enforced by the viewer.

| Feature | Device setting (`agent.toml` / `aegiron-agent set`) | Platforms |
|---|---|---|
| `view_only` | always listed | all |
| `block_input` | `allow_input` **and** `allow_block_input` (`--allow-block-input`) | macOS, Windows |
| `privacy` | `allow_input` **and** `allow_privacy_mode` (`--allow-privacy-mode`) | Windows 10 2004+; macOS only in the desktop app |
| `lock` | `allow_lock` (`--allow-lock`) | macOS, Windows, Linux (`loginctl lock-session`) |
| `restart` | `allow_restart` (`--allow-restart`) | macOS, Windows |

The four settings default to on (absent in older configs = on), as in RustDesk, and are in the app under Settings → ความปลอดภัย → การควบคุมเครื่องนี้จากระยะไกล. The connection manager shows them as permission tiles, and for each live session whether the viewer is in view-only mode, blocks input, uses privacy mode or will lock the machine at the end.

| Direction | Message |
|---|---|
| viewer→agent | `view_only {on}`, `block_input {on}`, `privacy {on}`, `lock`, `lock_after {on}`, `restart`, `ka` (keepalive) |
| agent→viewer | `ctl {op, ok, on?, message?}` for each of them (`op` = the message type); `ctl {op:"restart", ok:true, resume}`, and later `ctl {op:"restart", ok:false, message}` if the restart itself failed |
| viewer→agent | `auth {…, resume}`: reconnecting after the restart |

- Only screen sessions have controls: tunnel and terminal sessions send no `info`, ignore these messages and never accept a `resume` token.
- **View-only.** The viewer stops sending pointer and keyboard input (absolute, relative and on every extra display window); with `view_only` the agent also drops any input while it is on, whichever display stream it targets, and shows it in the connection manager. Viewers re-send it after reconnecting.
- **Block input.** The person at the machine cannot use its keyboard and mouse; the viewer's input still works. macOS: a CGEventTap at the HID level (Accessibility permission, which input injection needs anyway) drops events that were not posted by the agent's own process. Windows: low-level keyboard and mouse hooks drop events without the injected flag (`BlockInput` needs administrator rights and would block injected input too). Pointer movement, key and button releases, and clicks on Aegiron's own windows still pass, so the person can reach the connection manager and press ตัดการเชื่อมต่อ. **Ctrl + Alt + Shift + Esc** at the machine ends every session that blocks it (audited as `agent.denied {stage:"local_escape"}`). Hooks and taps belong to the agent process: the system removes them when it exits or crashes, and every session end (disconnect, error, kill from the connection manager) releases them.
- **Privacy mode** turns on input blocking too, and blacks out every display for the people in front of it while the viewer keeps seeing the desktop. Windows: topmost black windows with `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`, which every capture path (GDI, Windows Graphics Capture) leaves out; on Windows before 10 2004 the call fails and the agent answers `ok:false` rather than stream a black screen. macOS: borderless black windows at the shielding window level, created on the desktop app's main thread; while they are up the agent captures with `CGWindowListCreateImageFromArray` over every on-screen window except them (`NSWindow.sharingType = none` is not relied on: it only hides a window from other processes, and macOS 15 ignores it for ScreenCaptureKit). The headless `aegiron-agent` has no AppKit main loop, so it does not offer privacy mode on macOS. The black screen shows the escape combination.
- **Watchdog.** While input is blocked or privacy mode is on, viewers send `ka` every 10 s; an agent that hears nothing from the viewer for 30 s ends the session, so a viewer that vanished never leaves the machine blocked. Older agents ignore `ka`.
- **Lock.** macOS: `SACLockScreenImmediate` (login.framework), else ⌃⌘Q posted as a key event. Windows: `LockWorkStation`. Linux: `loginctl lock-session`. With `lock_after {on:true}` the agent locks the machine when the session ends however it ends (after unblocking input). Viewers talking to older agents still offer the lock shortcut as key presses.
- **Restart** (the viewers ask for confirmation first). The agent answers `ctl {op:"restart", ok:true, resume}`, waits about a second so the reply arrives, then restarts as the logged-in user: macOS `osascript -e 'tell application "System Events" to restart'` (apps are asked to quit like from the Apple menu, so one with unsaved work can cancel it; the first use asks the person at the machine to let Aegiron control System Events), falling back to `loginwindow` (`«event aevtrrst»`); Windows `shutdown /r /t 0`. No root or system service is involved. If the command fails the token is revoked and the viewer gets `ok:false`.
- **Reconnecting.** `resume` is 32 random bytes (base64url), single use, valid for 15 minutes and bound to the viewer's account (the console user's email from the session request). The agent keeps only its SHA-256 in `resume.json` next to `agent.toml` (owner-only), so it survives the restart. When the old session closes, the viewer shows *เครื่องปลายทางกำลังรีสตาร์ท* and requests new sessions with backoff (3 s, 6 s, 12 s, 24 s, then every 30 s, for up to 12 minutes) while the device is offline, and answers `auth_required` with `auth {password:null, resume}`. A valid token replaces both the password and the click approval (audited as `agent.auth_ok {method:"resume"}`) and does not rotate the temporary password. An unknown, expired or already used token is ignored and the usual checks apply, so the viewer falls back to asking for the password. The device comes back only if the agent starts at login (`aegiron-agent install` or the app's autostart) and a user logs in (automatic login, or someone at the machine; FileVault always needs a password at boot).
- **Audit** (`agent.<kind>`): `view_only {on}`, `block_input {on}`, `privacy_mode {on}`, `lock_screen {}` or `{after_session:true}`, `lock_after_session {on}`, `restart {}`, `restart_failed {error}`.

Pointer coordinates are normalised to 0–1 over the displayed frame. Plain typing uses the actual character (Thai and other layouts work). Shortcuts with Ctrl/Cmd/Alt use the physical key.

Authentication: 3 attempts per session; 5 consecutive failures lock the agent for 60 s. The temporary password rotates after every successful login.

### Displays, resolution and input modes

Agents from 0.6 add these to `info.features`; a viewer uses each only when it is listed, so older agents never see the new messages and older viewers never send them. `info.displays[]` entries also carry `x`, `y` (position in the same units as `width`/`height`) so a viewer can draw the layout.

| Feature | Direction | Message |
|---|---|---|
| `alldisp` | viewer→agent | `cfg {display_all: true}` streams every display as one picture (the bounding box of all displays, each placed by its position; mixed DPI is scaled to the densest display). `cfg {display: n}` goes back to one display. Pointer input, `cursor` and annotations are normalised over the whole picture. |
| `multidisp` | viewer→agent | `cfg {streams: [1, 2]}`: stream these displays *in addition* to the main one (at most 8; the full list each time, `[]` stops them). |
| `multidisp` | agent→viewer | Byte `0x06`: display u8, then a complete message of the main stream for that display (`0x02` rectangle, `0x04` video frame, or `0x01` JSON such as `cursor` and `encoder`). Quality, fps, codec and `refresh` apply to every stream. Extra streams are not recorded. |
| `multidisp` | viewer→agent | `mm {x,y,d}`, `mb {b,down,x,y,d}`: with `d` the position is normalised to display `d` instead of the main stream. |
| `resolution` | viewer→agent | `res_list {display}` → `res_list {display, current:{w,h,hz}, original:{w,h,hz}, modes:[{w,h,hz}]}` (`w`, `h` in the display's own units: points on macOS, pixels elsewhere; `hz` 0 when unknown) |
| `resolution` | viewer→agent | `res_set {display, w, h, hz?}` → `res_ok {display, w, h, hz}` and `displays {displays[]}` with the new sizes, or `res_error {display, message}`. `res_restore {display}` puts the original mode back. |
| `keymode` | viewer→agent | `cfg {keyboard: "map" \| "translate"}` (default `translate`) |
| `relmouse` | viewer→agent | `mr {dx, dy}`: relative pointer motion in the remote's input units (each clamped to ±2000). `mb {b, down}` without `x`/`y` presses where the pointer is. |

- **Resolution** is only offered when the host allows it (`allow_resolution`, default on; app Settings → ความปลอดภัย → อนุญาตให้เปลี่ยนความละเอียด, or `aegiron-agent set --allow-resolution false`) and the platform can do it: macOS (CoreGraphics `CGDisplayCopyAllDisplayModes` / `CGDisplaySetDisplayMode`, desktop-usable modes only) and Windows (`EnumDisplaySettingsExW` / `ChangeDisplaySettingsExW` with `CDS_FULLSCREEN`, so nothing is written to the registry). `info.resolution: true` says so. The agent remembers each display's mode before the first change and restores it when the session ends, however it ends. `AEGIRON_TEST_RESOLUTION=fake` in the agent's environment replaces the platform with an in-memory list of modes (tests; never set by the app or installers).
- **Keyboard modes.** `translate` (the default, and what older agents do) types the character of each key, so any layout works without the remote having it, and uses physical keys only for shortcuts with Ctrl/Cmd/Alt. `map` presses the physical key for every key (`code`), down and up, like a keyboard plugged into the remote machine: the remote's own layout decides the character (Thai typing then needs the Thai layout on the remote), and games see real key presses and releases. `text {s}` still types text in both modes.
- **Relative mouse** is for games and 3D apps that read raw motion: the browser uses pointer lock and the desktop app grabs and hides the cursor; both toggle it with Ctrl+Alt+M (Esc also leaves pointer lock in the browser).
- **Each display in its own window** (desktop app): the app keeps one session and asks for the other displays with `cfg {streams}`; each extra window renders its `0x06` messages and sends input with `d`.

## 5. Desktop app sign-in

```
app  → POST /api/agent/login {email, password, totp?, device}      (HTTPS, certificate verified)
     ← {need_totp: true}  |  {user, token, server_key, enroll_token}
```

- `token`: bearer token for the app (`Authorization: Bearer …`), 30 days, revoked by `POST /api/auth/logout`. Stored in the agent's `agent.toml` (owner-only file).
- `server_key`: the server's Ed25519 identity, trusted because it arrived over the server's own TLS. A signed-in device that already pins a different key refuses the sign-in.
- `enroll_token`: single-use, 1 hour, owned by the user. Registering with it sets `devices.owner_id` and adds the device to that user's address book.
- Opening the web viewer from the app: `POST /api/auth/handoff` (bearer) returns a code valid for 60 s and usable once; the browser opens `GET /api/auth/handoff/{code}?next=/connect/<id>`, which sets the console cookie and redirects. `next` must be a same-site path.

### Trusted devices ("remember this device for 30 days")

On the 2FA step a client may ask to be remembered. The trust token replaces only the TOTP code; the password is always checked first, and the brute-force limits apply as before.

```
web  → POST /api/auth/login  {email, password, totp, remember_device: true}
     ← Set-Cookie: aegiron_trust=<token>; Path=/api/auth; HttpOnly; SameSite=Strict; Secure; Max-Age=30 days
web  → POST /api/auth/login  {email, password}            (cookie sent automatically)  → {user}
app  → POST /api/agent/login {email, password, totp, device, remember_device: true}
     ← {user, token, server_key, enroll_token, trust_token}
app  → POST /api/agent/login {email, password, device, trust_token}                      → {user, token, …}
     ← {need_totp: true, trust_rejected: true}   when the token is expired, revoked or another user's
```

- The token is 32 random bytes (base64url). The server stores only its SHA-256 in `trusted_devices`, bound to the user, with a label (browser/OS, or the app's host name), user agent, first and last IP, created / last-used time and a fixed 30-day expiry (not extended by use). At most 20 per user; the oldest go first.
- A token is issued only in the same request as a correct TOTP code, and only if the account has 2FA. It travels in a request body or an HttpOnly cookie, never in a URL. The app keeps it in `agent.toml` (owner-only) per server and account, and keeps it after signing out; it is dropped on `trust_rejected`.
- Revocation: `GET /api/auth/trusted-devices` (the current browser is marked `current`), `DELETE /api/auth/trusted-devices/{id}`, `DELETE /api/auth/trusted-devices` (all). Admins: `GET|DELETE /api/users/{id}/trusted-devices[/{tid}]`. Every remembered device of a user is revoked automatically when the password is changed or reset, 2FA is enabled, disabled or reset, or the account is disabled.
- Audit: `auth.trusted_device_added`, `auth.login` / `auth.agent_login` with `trusted_device_added` or `trusted_device` (2FA skipped) in the detail, `auth.trusted_device_rejected`, `user.trusted_device_revoked {id, label, by}`, `user.trusted_devices_revoked {count, reason}`.
- SSO sign-in is unaffected: it never asks for TOTP (the IdP handles MFA) and never issues trust tokens.

### Sign-in code by email

An account without TOTP can use a 6-digit code sent by email as its second factor (`POST /api/auth/email-otp {enabled, password}`, needs outgoing mail to be set up). It uses the same fields as TOTP, so older apps work unchanged: after a correct password the server mails a code and answers `{need_totp: true, method: "email"}`; the client sends the code as `totp`. Codes last 10 minutes, are single use, at most one mail per minute, and five wrong codes burn the code (only its SHA-256 is stored, in `email_codes`). Remembered devices skip it like TOTP. If mail is not available the sign-in fails with `503 {code: "mail_unavailable"}` rather than skipping the factor. Admin `DELETE /api/users/{id}/totp` turns off both kinds. Audit: `auth.email_code_sent`, `auth.login_failed {reason: "bad_email_code"}`, `user.email_otp_enabled|disabled`.

### LDAP / Active Directory

`GET/PUT /api/ldap/settings` (admin): `url` (`ldaps://host` or `ldap://host`, which always uses StartTLS; there is no plaintext mode and no fallback), optional extra `ca_cert` (PEM, added to the system roots; certificates and host names are always verified), `bind_dn` / `bind_password` (service account, sealed with the vault key, never returned), `base_dn`, `user_filter` (`{username}` is replaced, escaped; default matches `uid`, `mail`, `sAMAccountName`, `userPrincipalName`), `email_attr`, `name_attr`, optional `group_filter` (`{dn}` = the user's DN; otherwise `memberOf`), `admin_groups`, `user_groups` (names or DNs), `auto_create`, `enabled`. `POST /api/ldap/test {username?}` binds the service account and shows what the directory returns for a user.

Both `POST /api/auth/login` and `POST /api/agent/login` accept a directory user name or email in `email`. Accounts that came from the directory (`auth_source: "ldap"`) are checked only against it: bind as the service account, find exactly one entry, bind as that entry with the password (never with an empty password). The account is created on first sign-in when `auto_create` is on. With `admin_groups` set, the role follows the directory at every sign-in; with `user_groups` set, others are refused. A local account with the same email is never taken over. TOTP or email codes still apply on top. Directory accounts cannot set a local password. `server-info.ldap` tells the login page to accept user names. Audit: `user.created {via: "ldap"}`, `auth.login_failed` with `reason` `bad_credentials`, `ldap_not_in_group`, `local_account`, `no_account`, `ldap_unavailable`, `ldap_disabled`; `ldap.settings_saved`.

### Mail and admin alerts

`GET/PUT /api/smtp/settings` (admin): `host`, `port`, `security` (`starttls`, the default and required when chosen; `tls` = implicit TLS; `none` only to a relay on localhost), optional `ca_cert`, `username` / `password` (sealed with the vault key, never returned), `from`, `alert_recipients` (empty = every enabled admin), `alert_new_device`, `alert_lockout`, `enabled`. `POST /api/smtp/test {to?}` sends a test message. Alerts: a device registering for the first time, and an account hitting the sign-in limit (10 attempts in 10 minutes, audited once per window as `auth.lockout`). Audit: `smtp.settings_saved`, `smtp.test`.

### Shared address books

Besides each user's personal address book (`/api/address-book`), users can create shared books: `GET/POST /api/address-books`, `PATCH/DELETE /api/address-books/{book}`, `GET /api/address-books/{book}/entries`, `PUT/DELETE /api/address-books/{book}/entries/{id}` (`{alias, tags, note}`), `GET/PUT /api/address-books/{book}/shares` (`{shares: [{user_id | group_id, permission}]}`), `GET /api/share-targets`. Permissions: `read` (see entries), `rw` (also add, edit, remove entries), `full` (also rename, delete and share). The owner and admins always have full access; a user shared directly and through a group gets the highest. Seeing a device in a book does not grant access to it: the access policy and the device password still apply. Audit: `address_book.created|updated|deleted|shared|entry_saved|entry_removed`.

### Organisation SSO (OpenID Connect)

- Browser: `GET /api/oidc/login?next=` → identity provider (Authorization Code + PKCE, `state`, `nonce`, bound to the browser by a cookie) → `GET /api/oidc/callback`. The ID token is verified (signature, issuer, audience, expiry, nonce); `email_verified` and the allowed domains are enforced. TOTP is not asked again: the IdP is responsible for MFA.
- App: `POST /api/oidc/auth {device}` → `{code, url, expires_in}`. The app opens `url` in the browser. That page shows the requesting device and IP before continuing to the IdP. The app polls `GET /api/oidc/auth-query?code=` every 2 s and gets `{pending:true}`, or the same payload as `/api/agent/login`. The poll code never appears in the browser URL.
- Admin: `GET/PUT /api/oidc/settings`. The client secret is sealed with the vault and never returned.

## 6. Agent updates

- Admins upload builds: `POST /api/agent/releases` (multipart, up to 300 MB, stored by SHA-256), then enable or disable them.
- Clients check with `GET /api/agent/update?os=&arch=&version=`, which returns the newest enabled release that is newer by semver.
- Clients download from `GET /api/agent/releases/{id}/download`, served with `X-Checksum-SHA256`.
- The app downloads only after the user asks, from the same server only. It keeps the file only if the size and SHA-256 match, and never installs it by itself.

## 7. Session recording

Sessions are end-to-end encrypted, so the server cannot record them. The **controlled device** records what it streams and uploads the file afterwards.

- Policy (admin, web console → บันทึกเซสชัน): `GET/PUT /api/recordings/settings` `{mode: "off"|"all"|"groups", group_ids[], retention_days}` (0 = keep until deleted). Stored in `settings` under key `recording`.
- When a session must be recorded, the server creates a `pending` row in `session_recordings` and adds `"record": {"token", "upload"}` to the agent's `session` message. The token is single-use (only its SHA-256 is stored) and valid for 7 days. Agents that predate recording ignore the field and stream unrecorded.
- After authentication the agent starts the recorder and reports `{"t":"event","kind":"recording_started"}` (or `recording_failed`; if the recorder cannot start, the session is refused with `auth_result {ok:false, reason:"recording_failed"}` rather than run unrecorded). The approval prompt says the session will be recorded; `info` carries `"recording": true` so viewers show **กำลังบันทึก**, and the connection-manager window on the controlled machine shows the same badge for the whole session.
- Upload, after the session ends (and retried whenever the agent reconnects; files cut off by a crash are truncated to the last complete record and uploaded too):

  ```
  POST /api/agent/recordings/{sid}
  Authorization: Bearer <record.token>
  X-Aegiron: 1
  X-Aegiron-Signature: base64 Ed25519(device key, "aegiron-recording-v1\n" + device_id + "\n" + sid + "\n" + hex(SHA-256(body)))
  body: the .aerec file
  ```

  Only over HTTPS with a verified certificate, or plain HTTP to loopback; `allow_insecure_transport` does not apply. The server checks the token, the signature against the device's registered key, and the file structure (header `sid`/`device_id` must match), then stores it as `<AEGIRON_DATA_DIR>/recordings/<sid>.aerec` (limit `AEGIRON_RECORDING_MAX_MB`, default 4096). 400/401/404/409/413 are final (the agent deletes its copy); anything else is retried.
- Admin only: `GET /api/recordings[?device=]`, `GET /api/recordings/{id}`, `GET /api/recordings/{id}/file` (Range supported), `DELETE /api/recordings/{id}`. Audit: `recording.uploaded`, `recording.rejected`, `recording.viewed`, `recording.deleted`, `recording.purged`, `recording.settings_updated`, plus `agent.recording_started` / `agent.recording_failed`. Retention runs at start-up and hourly.

### Container (`.aerec`)

```
"AEGREC1\n"
u32 BE header length, JSON header {"v":1,"sid","device_id","hostname","os","started_ms"}
records until EOF: u32 BE milliseconds since start, u32 BE payload length (1..32 MiB), payload
```

A payload is a plaintext channel message exactly as streamed: `0x04` H.264 or AV1 frames, `0x02` JPEG rectangles (a session can switch codecs, e.g. from AV1 to H.264 or from H.264 to JPEG), `0x01` `cursor` messages and `0x05` audio packets. Clipboard, file chunks and other control traffic are not recorded. The last record is `{"t":"end"}` so idle time at the end counts. The browser plays it with WebCodecs (H.264, AV1) and `createImageBitmap` (JPEG), seeking from the nearest video keyframe or full-screen JPEG rectangle. The server's recording `codec` lists the codecs found, `+`-joined in the order h264, av1, jpeg (e.g. `h264+jpeg`).

Audio (recordings made before audio was recorded have no `0x05` records and play as before):

- The agent records exactly the `0x05` packets it sends to the viewer, timestamped like video when they are sent. A session without audio (`info.audio` false: the viewer did not ask for it, the device does not allow it with `allow_audio`, or the platform cannot capture) records none. While the viewer has muted audio (`{"t":"audio","on":false}`), no packets are captured or sent, so that stretch of the recording is silent. Packets the agent drops under congestion are missing from the recording too.
- The container stays `AEGREC1` / header `v:1`: readers skip record types they do not know, so older servers accept these files and older consoles play them without sound. The server validates `0x05` records (codec byte, sequence, at least one byte of Opus) and stores `audio = "opus"` on the recording when it has any (`GET /api/recordings` field `audio`, `""` otherwise).
- Playback: the browser places consecutive packets 20 ms apart by sequence number while that stays within 100 ms of their record time (a sequence gap or larger drift starts again at the record time), decodes them with WebCodecs `AudioDecoder` (a new decoder for each run of consecutive packets, since Chrome stamps decoder output by counting samples from the first chunk) about 400 ms ahead of the playback position and schedules each block in Web Audio at the time that matches the video clock. Seeking, pausing and changing speed drop everything scheduled and restart from the new position, so audio and video cannot drift apart. Sound plays at 1× and 2× (`playbackRate`, pitch not corrected) and is silent at 4× and 8×. The player has a mute button (key `m`); if the browser blocks autoplay, the button asks for a click. The desktop app has no recording player.

## 8. Whiteboard (annotations)

The viewer draws on the remote screen; the controlled machine shows the strokes in a transparent, click-through, always-on-top window over the streamed display. Only the desktop app (`aegiron`) can show it; the headless `aegiron-agent` never offers it.

- Negotiation: `info.whiteboard: true` when the agent allows it (`allow_whiteboard`, default on; app Settings → ความปลอดภัย, or `aegiron-agent set --allow-whiteboard false`) and a desktop UI is attached. Viewers show the pen only then; older agents never set it, older viewers never send strokes.
- viewer→agent (JSON inside the encrypted channel):
  - `wb {op:"line", id, c:"#rrggbb", w, p:[x0,y0,x1,y1,...]}` appends points to stroke `id` (created on first use with color `c` and width `w`, a fraction of the display height). Points are normalised 0–1 over the displayed frame, like pointer input.
  - `wb {op:"clear"}` removes all strokes.
- Limits on the agent: 1024 points per message, 300 strokes, 60 000 points (oldest strokes go first). Strokes stay until cleared; they disappear when the session ends or the viewer switches display. The overlay is part of the screen, so the stream (and a recording) shows it too.

## 9. Direct connections (LAN/TCP and P2P) and proxies

A native viewer can reach the agent without the relay. The bytes on a direct path are the same WebSocket messages as on the relay (`paired`, then the §3 handshake and the §4 encrypted channel, unchanged), so a direct path gains no trust: the agent is still authenticated by its device key, and the viewer by the password or click inside the channel. The browser viewer always uses the relay.

**Negotiation (feature flags, so old peers keep working)**

- The agent adds `"features":["direct1"]` (and its NAT type as `nat`) to `register`. Servers that do not know it ignore the field.
- `registered` may carry `udp_port` (rendezvous / NAT probe). Older agents ignore it.
- The viewer asks with `POST /api/sessions?direct=1`. Older servers ignore the query flag. Without it, nothing below happens.
- The server offers a direct path only if the viewer asked, `AEGIRON_P2P` is on (default) and the agent advertised `direct1`. Then the session request gets `"direct":{"token":T,"punch_key":Ka,"udp_port":P}`, where `T` is a fresh per-session secret and `Ka` is the agent's rendezvous key (`punch_key`/`udp_port` are present only when UDP is enabled).
- The agent answers on signaling with `{"t":"direct_offer","sid","tcp":["ip:port",...],"cert":<hex SHA-256 of its per-session QUIC certificate>,"nat"}`, or with `{"t":"direct_offer","sid","disabled":true}` when its policy (`direct_enabled = false`) forbids direct sessions. The server waits for the offer for at most 2.5 s. It keeps up to 8 valid unicast candidates, adds the agent's public IP as the server sees it (with the listening port), and returns `ticket.direct = {token: T, tcp: [...], quic: {cert, punch_key: Kv, udp_port: P}, nat}` to the viewer. `Kv` is the viewer's own rendezvous key.

**Token proof on every direct path.** The viewer opens a WebSocket (`GET ws://aegiron-direct/`) over the path with the header

```
aegiron-direct: v1 <sid> <viewer_epk_b64> <base64 HMAC-SHA256(T, "aegiron-direct-v1\n" + sid + "\n" + viewer_epk_b64)>
```

The agent checks it during the HTTP upgrade, before any WebSocket frame: the sid must be a session that is waiting for its viewer, the MAC must verify (constant time), and at most 6 connections are accepted per session. Anything else gets `403` and is closed. The agent then sends `{"t":"paired","path":"direct"|"p2p"}` and accepts only a `hello` whose `epk` equals the key in the header, so a sniffed header cannot be reused with another key. The token never crosses the network in clear: it reaches the viewer over the server's HTTPS and the agent over signaling. The direct TCP port is rate-limited to 30 unauthenticated attempts per minute per source address and 16 handshakes at a time. The port opens with the first direct offer and rejects everything unless a session with a direct offer is waiting for its viewer. Each per-session QUIC endpoint accepts for at most 20 s.

**Paths**

- **Direct (TCP)**: the agent listens on `direct_port` (default 21118, a random port if it is taken) and offers its LAN IPv4 addresses. With a port forward, the public address the server adds also works.
- **P2P (QUIC over UDP hole punching)**: each side sends `{"t":"punch","sid","role":"agent"|"viewer","ts","mac":base64 HMAC-SHA256(K, "aegiron-punch-v1\n"+sid+"\n"+role+"\n"+ts)}` from the socket it will use to the server's UDP port `P`, and repeats until the reply `{"t":"punch","addr":<own public address>,"peer":<other side's>}` names the peer. The first authenticated address per role wins, and the rendezvous closes once the session is direct. Both then send a few datagrams to the peer to open their NAT mappings. The agent runs a QUIC server (TLS 1.3, ALPN `aegiron-direct/1`) on that socket with a self-signed certificate made for this session. The viewer pins it by the SHA-256 from the ticket and accepts no other certificate. The WebSocket runs on one bidirectional QUIC stream. QUIC (quinn, ring) gives reliable, ordered, congestion-controlled delivery with keep-alives, which the counter-based AEAD channel requires.
- **NAT probe** (like RustDesk's NAT test port): the server answers `{"t":"nat"}` with `{"t":"nat","addr":"ip:port"}` on UDP `P` and `P+1`. The agent sends from one socket to both: different mapped ports means a *symmetric* NAT (hole punching usually fails), the same means *cone*, and a mapped address equal to a local one means *open*. The result is shown in Settings → Network and sent as `nat`. UDP requests shorter than 96 bytes are ignored and replies are never larger than the request (no amplification), with at most 20 packets per second per source.

**Choosing a path.** The viewer starts every candidate at once (TCP to each address, QUIC). The relay starts after a 2.5 s head start, or at once if every direct attempt has already failed, and direct attempts give up after 9 s. The viewer sends its `hello` on the first path that answers `paired`. The agent joins the relay as before and waits on all paths: the first `hello` wins and the others are dropped. If nothing is offered, or both policies allow it but no direct path works, the session runs on the relay exactly as before. The viewer shows the path (relay / direct / P2P) in its connection info.

**Audit.** When the agent accepts a hello on a direct path it sends `{"t":"direct_started","sid","path":"direct"|"p2p"}`. The server writes `session.start` with `path`, marks the session started, and closes the agent's unused relay slot (a viewer can no longer join it). When the session ends, the agent sends `{"t":"direct_ended","sid","reason","bytes_to_viewer","bytes_to_agent"}` and the server writes `session.end` with `path` and the byte counts. If the agent's signaling connection drops while a direct session runs, the server ends that record with `reason: "agent_offline"`. Relay sessions now also carry `"path":"relay"` in their audit detail. Agent events (`agent.*`) of direct sessions are attributed to the viewer as before.

**Policy.** Server: `AEGIRON_P2P=false` turns off direct and P2P sessions for everyone. `AEGIRON_UDP_PORT` (default `21116`, which also uses `21117`; `0` = off) controls hole punching and the NAT probe; LAN/TCP direct sessions still work without it. Open these UDP ports in the firewall: a TLS reverse proxy such as Caddy does not carry them. Device: `direct_enabled = false` in `agent.toml` (Settings → Network → อนุญาตการเชื่อมต่อโดยตรง, or `aegiron-agent set --direct false`) makes the agent decline every offer and the app's viewer use only the relay.

**Proxy.** `[proxy]` in `agent.toml` (`kind = "socks5" | "http"`, `host`, `port`, optional `username`/`password`, stored like the other secrets in the owner-only file; Settings → Network → พร็อกซี, or `aegiron-agent set --proxy socks5://host:port --proxy-user NAME`, which prompts for the password) sends every connection to the server through a SOCKS5 tunnel (RFC 1928 with username/password, RFC 1929; the proxy resolves the name) or an HTTP `CONNECT` tunnel (`Proxy-Authorization: Basic`). This covers signaling, relay and the HTTPS API (sign-in, address book, sessions, updates). TLS to the server runs inside the tunnel with the same certificate verification as without a proxy. Credentials are refused in proxy addresses and never appear in URLs. Direct and P2P paths do not use the proxy; turn them off where all traffic must go through it.

`aegiron-agent connect <ID> [--only relay|direct|p2p]` runs the app's viewer from a terminal and prints the path it used, which helps diagnose a deployment.

## 10. `aegiron://` links and the single app instance

- Links: `aegiron://connect/<id>` or `aegiron://<id>` (also `redesk://`), where `<id>` is 9 digits (spaces or `%20` allowed). Nothing else is accepted: no query string, no extra path, no password. The app always asks before connecting.
- macOS delivers links as a `kAEGetURL` Apple Event, at launch and while the app runs. The app handles it with `NSAppleEventManager` (installed before the event loop starts and again after launch). Windows passes the link as the first argument.
- One app instance per user and config file. The first instance holds an exclusive lock on `instance.lock` next to `agent.toml` and listens on a Unix socket `instance.sock` there (folder 0700, socket 0600) or, on Windows, on the named pipe `\\.\pipe\aegiron-<first 8 bytes of SHA-256(config path), hex>` (remote clients rejected; other users cannot write to it). A second launch sends one message, `aegiron-show` or `aegiron-open <9-digit id>` (at most 64 bytes, parsed strictly), and exits.

## 11. TCP tunnels and remote terminals

Two session types that stream no screen, like RustDesk's *TCP tunneling* and *terminal*. They use the same session request, relay or direct path, handshake (§3) and authentication (password and/or approval, lockout, one-time password rotation) as remote control; only what follows `auth_result {ok:true}` differs.

**Negotiation (old peers refuse cleanly)**

- Agents that run them add `"tunnel1"` and `"terminal1"` to `register.features`.
- The viewer asks with `POST /api/sessions {device_id, type: "tunnel", target: "host:port"}` or `{device_id, type: "terminal"}` (absent `type` = `"screen"`). The target is `host:port` (`[v6]:port`) as seen from the controlled machine; the host name is lower-cased. A bad target or type is `400`. An online agent that did not advertise the feature gets nothing and the viewer gets `422 the device's Aegiron version does not support this session type`. Older servers reject the unknown fields with `400`.
- The ticket always carries `type` (and `target`); viewers of tunnels and terminals refuse a ticket without the type they asked for. The agent's `session` request carries `"type"` and `"target"`; older agents never receive one.
- The viewer repeats the type in `auth {…, session: "tunnel"|"terminal", target}`. If it differs from the server's request the agent answers `auth_result {ok:false, reason:"session_mismatch"}`. After authentication the agent sends `info {session, hostname, os, …}`; a viewer that gets an `info` without the expected `session` (an agent that started a screen session) closes.

**Device permissions** (off by default; checked right after the handshake, before any password is used, refused with `auth_result {ok:false, reason}` and reported as `agent.denied {reason, session, target}`):

| Setting (`agent.toml`, app Settings → ความปลอดภัย, `aegiron-agent set`) | Default | Refusal |
|---|---|---|
| `allow_tunnel` / `--allow-tunnel` | off | `tunnel_disabled` |
| `allow_tunnel_lan` / `--allow-tunnel-lan`: tunnels may also reach private networks (10/8, 172.16/12, 192.168/16, 169.254/16, fc00::/7, fe80::/10) | off: loopback only | `target_not_allowed` |
| `allow_terminal` / `--allow-terminal` | off | `terminal_disabled` |

Tunnels never reach public addresses. The agent resolves the target itself; every address the name resolves to must be allowed, and only those addresses are connected to. The approval prompt says what is asked ("เปิด TCP tunnel ไปที่ localhost:3389", "เปิดเทอร์มินัล (shell) บนเครื่องนี้"), and the connection manager shows it for the whole session.

**Recording.** Tunnelled traffic cannot be recorded: when the policy records a device (§7), `POST /api/sessions` refuses tunnels with `422` and audits `session.denied {reason: "recording_required"}` (an agent that still gets a recording token for a tunnel refuses with `recording_required`). Terminal sessions are recorded like `script(1)`: the agent records the `0x11` output it sends and `{"t":"term_size","cols","rows"}` at start and on every resize, never the keystrokes. The server stores such recordings with `codec = "terminal"`, and the console plays them in xterm.js with their timing.

**Audit.** `session.request`, `session.start` and `session.end` (relay and direct) carry `type` and, for tunnels, `target`; so do the agent events of the session. Agent events: `tunnel_open {target}`, `tunnel_closed {target, connections, bytes_up, bytes_down}`, `terminal_open {shell, cols, rows}`, `terminal_closed {reason: "exited"|"viewer_left"|"local_user", code?}`. `GET /api/sessions` lists `type` and `target` (column `remote_sessions.kind`/`target`, migration `010_session_types.sql`).

Both ends send `{"t":"ping"}` at least every 30 s while idle (ignored by the receiver) and give up after 120 s without any message.

### Tunnels

The viewer listens on `127.0.0.1:<local port>` (bound before the session starts, so a busy port fails at once) and turns every accepted connection into a stream; the agent connects each stream to the session's target. Up to 64 streams at a time.

| Direction | Message |
|---|---|
| viewer→agent | `tcp_open {id}` (`id` u32, non-zero, chosen by the viewer) |
| agent→viewer | `tcp_opened {id}`, or `tcp_error {id, message}` (connect failed or refused; the viewer closes the local connection) |
| both | `0x10` data: stream id (u32 BE) followed by 1–32 KiB |
| both | `tcp_ack {id, n}`: `n` bytes of that stream were written to the local socket |
| both | `tcp_eof {id}`: the sender's socket reached end of file (half-close): the receiver shuts down the write side of its socket after the data before it, and may keep sending |
| both | `tcp_close {id}`: the sender's socket failed; the receiver drops the stream |

Flow control: a side never has more than 256 KiB of a stream unacknowledged, and acknowledges only what it has written to its socket, so a slow consumer slows its own stream and nothing else; a peer that exceeds the window gets `tcp_close`. A stream is gone once both directions sent `tcp_eof`, or after `tcp_close`. The info message carries `target`, `window` and `max_streams`.

Clients: `aegiron-agent tunnel <id> <local>:<host>:<port>` (password prompted or `AEGIRON_REMOTE_PASSWORD`), and in the app the peer menu's *TCP tunnel…* (local port, host, port, presets RDP/SSH/VNC/HTTP; on Windows it can start `mstsc` on the local port once open). Open tunnels are listed at the bottom right with their connections and traffic until stopped.

### Terminal

After `info` the viewer sends `term_open {cols, rows}`; the agent then starts the user's shell (`$SHELL`, else the account's shell, else `/bin/sh`, as a login shell; on Windows PowerShell, else `%COMSPEC%`) in a pseudo-terminal (openpty, ConPTY on Windows) in the home folder, with `TERM=xterm-256color`, `LANG=en_US.UTF-8` when no locale is set, and answers `term_started {shell}`. It runs as the agent's user.

| Direction | Message |
|---|---|
| agent→viewer | `0x11` + PTY output (raw bytes; UTF-8 can be split across messages) |
| viewer→agent | `0x11` + keystrokes as a terminal sends them (Ctrl-C is byte `0x03`, which the PTY turns into SIGINT) |
| viewer→agent | `term_resize {cols, rows}` (2–500 × 1–300) |
| agent→viewer | `term_exit {code, message?}` when the shell exits (`message` when it could not start); the session then ends |

Clients: the console's `/terminal/<id>` (xterm.js 5.5.0, menu *เทอร์มินัล* on a device), the app's terminal window (peer menu *เปิดเทอร์มินัล*; a VT100/xterm renderer with 256 colours, scrollback, paste, Thai through the system Thai font), and `aegiron-agent terminal <id> [--command CMD]` (raw mode on macOS/Linux; with `--command` it runs `CMD`, then `exit`, and returns the remote status).
